# Backend Lead

## Mission

The Backend Lead owns the quality, correctness, and maintainability of all .NET 8 code in the Maintain platform. In an AI-native engineering organization, this role is primarily a quality supervision and pattern enforcement function: the AI agents generate the code, and the Backend Lead ensures that code is architecturally correct, performant, secure, and maintainable before it reaches production.

The Backend Lead is the domain expert for EF Core patterns, Clean Architecture implementation, multi-tenancy enforcement, FluentValidation, and the .NET-specific conventions of this codebase. When AI-generated code violates any of these, the Backend Lead catches it.

---

## Responsibilities

### Code Review Leadership

Own the PR review process for all backend code. In an AI-native team, this means reviewing AI-generated PRs with a pattern-recognition mindset rather than a line-by-line mindset. The Backend Lead is not re-reading every line of code — they are scanning for the most common failure modes of AI-generated .NET code in this specific codebase.

The primary failure mode categories to watch for:
- EF Core anti-patterns (N+1 queries, missing AsNoTracking on read-only paths, lazy loading enabling where explicit loading is required, sync-over-async via .Result or .Wait())
- Multi-tenancy violations (missing TenantId filter in manual queries, using FirstOrDefault without tenant context, raw SQL without tenant parameter)
- Business logic in wrong layer (validation logic in domain entities that should be in FluentValidation, calculation logic in controllers that should be in Application/Calculations/)
- FluentValidation gaps (missing validators for new commands, validation rules that don't cover edge cases)
- Missing error handling (unhandled exceptions in handlers, missing 404 returns for not-found entities)
- Security issues (missing authorization attributes, tenant isolation gaps, user-supplied data used in SQL without parameterization)

### Pattern Library Maintenance

Own the base classes, extension methods, and utility classes that AI agents should use when generating code. Well-designed base classes reduce the surface area for AI agent errors: if the correct pattern is a one-liner (extend `BaseQueryHandler<TQuery, TResult>`), AI agents are less likely to invent an incorrect implementation.

Maintain: BaseQueryHandler, BaseCommandHandler, BaseRepository, TenantedQueryExtensions (for applying tenant filters), AuditableEntity (for entities needing audit fields), ValidationBehavior (MediatR pipeline behavior for FluentValidation), ErrorHandlingBehavior.

When a new cross-cutting pattern is needed (e.g., all command handlers need to emit domain events), the Backend Lead designs the base class implementation and documents it before AI agents start using the new pattern.

### Integration Test Health

Own the integration test suite for backend logic. Integration tests run against a real PostgreSQL + PostGIS instance spun up by Testcontainers. The Backend Lead ensures:
- Every new API endpoint has at least one integration test covering the happy path and one covering a validation failure
- Every multi-tenancy boundary has an integration test verifying tenant isolation (a user from Tenant A cannot see Tenant B's data)
- Database migrations are tested (the test suite runs with migrations applied, not just EF model state)

Monitor the integration test suite health daily. Flaky tests are investigated and resolved within 48 hours; a flaky test suite is worse than no test suite.

### Performance Profiling

Monitor database query performance. In an AI-native team, query performance issues tend to accumulate faster than in a traditional team because AI agents generate code rapidly and don't have the visceral cost-of-query intuition that experienced backend engineers develop. The Backend Lead runs weekly query analysis: examine the slowest 10 queries from the last 7 days (using PostgreSQL pg_stat_statements), identify any that were generated by AI and need optimization.

Add query performance acceptance criteria to integration test stories: "All queries on the asset list endpoint must complete in < 200ms with a 10,000-asset dataset."

## Authority

The Backend Lead has authority to:
- Block a PR for pattern violations, with specific citations to the relevant ADR or base class
- Require integration tests before merging a new feature
- Mandate a performance fix before a feature ships to production
- Update base classes and pattern libraries (with Architect review for significant changes)

The Backend Lead does not have authority to:
- Change the product scope or feature design
- Override the Architect on architectural decisions
- Deploy to production independently

**Monthly**: Backend code quality report (violation trends, test coverage, security scan results), pattern library update log

## Decision Making

When reviewing AI-generated code, the Backend Lead uses a fast triage approach:

1. **Run the automated checks first**: Does the build pass? Do all tests pass? Does the architecture test suite pass? If any of these fail, the PR is blocked regardless of code quality.

2. **Scan for the top-10 failure modes**: In 10 minutes, a pattern-recognition scan can catch 90% of the significant issues in an AI-generated PR. This is the primary review activity.

3. **Deep review for high-risk changes**: Migrations, security-related code, multi-tenancy logic, and Calculations/ code get line-by-line review from the Backend Lead or a senior backend engineer.

4. **Log patterns for agent improvement**: Every time a PR is blocked for a pattern violation, note whether the constraint document should be improved to prevent recurrence.

**08:00–08:30** — Review overnight CI results. Any integration test failures? Any performance regressions in the last deployment? Triage and assign investigation.

**08:30–10:30** — PR review queue. Work through backend PRs in priority order (unblocking engineers comes first). Target: zero PRs waiting more than 4 hours for review during business hours.

**10:30–11:00** — Check the automated architecture review output (if configured: a nightly job that scans all backend code for pattern violations using Roslyn analyzers). Review any new flagged items.

**11:00–12:00** — Active backend work: base class maintenance, integration test writing for new features, performance investigation.

**14:00–15:00** — Weekly deep work: run query performance analysis, review the weekly violation log, update agent constraint documents if patterns are emerging.

**15:00–17:00** — Mentoring and pair review: work with engineers on complex backend problems, walk through pattern violations found in review, explain the architectural reasoning.

## Collaboration

**With Tech Architect**: Daily alignment on patterns. The Architect designs the patterns; the Backend Lead implements them. When the Backend Lead finds that AI agents are consistently misusing a pattern, they bring it to the Architect to jointly update the constraint documentation.

**With AI Engineer**: Partnership on the Calculations/ layer — the most mathematically sensitive code in the backend. The AI Engineer owns the algorithm correctness; the Backend Lead owns the implementation quality (performance, error handling, test coverage).

**With QA Lead**: Close partnership on integration test strategy. The QA Lead owns test architecture; the Backend Lead owns backend integration test implementation.

**With Frontend Lead**: API contract alignment. When a frontend need requires a new API endpoint design, the Backend Lead and Frontend Lead agree on the contract before either implements it. This prevents the common failure mode of an API that doesn't match what the frontend actually needs.

---

## Escalation

The Backend Lead escalates to the ED when:
- A pattern violation has been introduced and built upon across multiple PRs (requires a planned refactoring sprint item)
- A performance issue is severe enough to require architecture intervention
- A security finding requires immediate action before the next planned sprint

---

## Continuous Improvement

Weekly: review the violation log. Are the same violations recurring? If so, the agent constraint document needs improvement. Draft an improved version and validate it against the next 5 AI-generated PRs.

Monthly: benchmark query performance against the previous month. Is the trend improving, stable, or degrading? Degrading performance is always investigated — it rarely self-corrects.

Quarterly: review the integration test suite for coverage gaps. What new features shipped in the last quarter that don't have adequate integration test coverage?

## Example Scenarios

### Scenario 1: Catching a Multi-Tenancy Violation

An AI-generated PR adds a new "Dashboard Summary" endpoint. The handler queries the database to compute portfolio health metrics. During review, the Backend Lead spots the query:

```csharp
var assets = await _context.Assets.Where(a => a.Status == AssetStatus.Active).ToListAsync();
```

The TenantId filter is missing. In a multi-tenant database, this query returns assets from all tenants, which is a critical data isolation violation. The EF Core global query filter should have caught this — but the AI bypassed it by not using the repository pattern that applies the filter.

The Backend Lead blocks the PR, provides the corrected version (using the repository's `GetAllAsync()` method which applies the filter), and notes in the violation log that the constraint document needs to explicitly state: "Never query DbContext directly for tenant-scoped entities. Always use the repository methods."

### Scenario 2: Resolving a N+1 Query in Capital Plan Loading

The capital plan list endpoint is performing poorly in the performance dashboard — P95 latency has gone from 140ms to 890ms as one agency's capital plan has grown. The Backend Lead runs the query analysis and finds the culprit:

```csharp
var plans = await _planRepository.GetAllAsync();
foreach (var plan in plans)
{
    plan.Projects = await _projectRepository.GetByPlanIdAsync(plan.Id);
}
```

This is a classic N+1: one query for plans, then one query per plan for projects. With 120 plans, that's 121 database round-trips.

The fix: a single query with Include() or a batch load using IDs. The Backend Lead implements the fix, writes a performance integration test that asserts the endpoint completes in under 200ms with 200 plans, and updates the constraint document with a concrete N+1 example to prevent recurrence.

### Scenario 3: Enforcing Calculation Isolation

An AI-generated PR implements the RUL calculation directly in the query handler:

```csharp
var rul = (asset.ConditionScore - threshold) / deteriorationRate;
```

This is a violation of the Calculations/ isolation principle: all calculation logic belongs in `Application/Calculations/`, not in handlers. Calculations in handlers cannot be unit-tested in isolation, cannot be reused, and couple business logic to the query execution path.

The Backend Lead blocks the PR, explains the violation, and provides guidance: move the calculation to `RulCalculator.cs` in `Calculations/`, write a unit test in `UnitTests/Calculations/RulCalculatorTests.cs`, and call `_rulCalculator.Calculate(asset, threshold)` from the handler. After the fix, the unit test coverage on the calculation is 100%.
